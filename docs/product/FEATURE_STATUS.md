# Feature Status — verified against code

Generated by reading the source at commit `8cbefef` (stage `.alpha3`, marketing
`0.1.0`, build 2). Every claim below is a `grep` result against the tree, not a
restatement of a document. Where a document and the code disagree, the code wins
and the disagreement is called out.

A Release build shows the features the train has reached. A Debug build shows
everything, because `ReleaseTrain.gate` returns all features under `#if DEBUG`.
"Always on" below means no gate asks about it, in any configuration.

### Gated "on" but actually always on — 2

`certificateStudio` (declared alpha1) and `appStore` (declared alpha3) have
**zero** `ReleaseTrain.isAvailable` call sites. Certificates is presented
unconditionally from Settings; App Store is a tab, and tabs were deliberately
taken out of the gate. So both were visible in every Release build, including
`v0.0.1-dev.1`, while the train claimed they arrived at alpha1 and alpha3.

## Not working

### 1. Three recorded "never" claims — by design

| Claim | Proof in code |
|---|---|
| In-app installation | `InstallationCapability.swift:118` — `deliveryMechanismAvailable = false` |
| Device pairing / JIT / usbmuxd | `PairingCapability` — no path reports supported |
| Off-device analytics | `AnalyticsPolicy.swift:30,38` — `isEnabled = false`, `endpoint: URL? = nil` |

These are decisions, not gaps. No stage promotion changes them.

### 2. Five features declared on the train but never gated

| Feature | Declared | Reality |
|---|---|---|
| `smartWorkspace` | rc2 | **Was leaking — now gated.** `CompositionRoot:126` constructed `SmartWorkspaceService` unconditionally, so `SigningView:1045` and `ApplicationDetailView:270` wrote `SmartWorkspace.json` on every sign at every stage, from `dev1` onward. The construction is now behind `ReleaseTrain.isAvailable(.smartWorkspace)`, which the two call sites already survive via `?.`. |
| `certificateStudio` | alpha1 | Always on (see above) |
| `appStore` | alpha3 | Always on (see above) |
| `batchSigning` | beta3 | `BatchSigningCoordinator` exists, **zero references in app code** |
| `signingHealthScore` | stable | `SigningHealthAssessment` exists, **zero references in app code** |

The release record therefore overstates precision in two directions at once:
two features ship earlier than declared, and one runs earlier than declared
while remaining invisible.

### 3. Two dead views — out of 103

- `SmartWorkspaceView` (`Presentation/Nova/`) — never presented. Its service
  writes state that nothing reads.
- `ExportDetailView` (`Presentation/`) — never presented.

The other 101 view structs are all referenced from app code.

### 4. One dead environment shim

`ExportsPresentation` declares `isAvailable: Bool = false` and exposes
`defaultValue`, but it is **never injected and never read**. `ImportPresentation`
is injected with `isAvailable: true` and `SigningQueuePresentation` with
`SigningQueueAvailability.isAvailable` (= `signingQueue && smartSign`) — both
live. Only the exports shim is orphaned; the `ExportCenter` behind it is real.

### 6. Bugs and unverified paths

- **`.p12`/`.pfx` certificate import is undiagnosed.** Never root-caused. The
  400 ms IPA/tIPA picker race was fixed, but that path is a tab, not a sheet,
  and does not explain it. Not claimed as fixed.
- **Navigation fixes are compile- and audit-verified only.** CI proves the code
  builds and `audit_navigation_stack.py` proves no pushed view opens its own
  stack. Only a real run proves the runtime agrees.
- **The import-picker race fix is the same** — statically verified, never
  observed working.
- **The private device matrix has never run.** Per `docs/releases/Checklist.md`
  §3, every release including this one is *Blocked* until a Release build is
  exercised on two real devices (one iOS 17, one iOS 18) plus a simulator smoke.

### 7. Not a problem, for the record

Zero `#if DEBUG` blocks in `ZynSign/Presentation` — all UI compiles into every
build. The Debug override lives only in `ReleaseTrain.gate`. Only 2 `XCTSkip` in
2,711 tests.
