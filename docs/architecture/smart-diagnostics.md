# Smart Diagnostics & Signing Health

Signing Health is a **read-only, local pre-sign observation**. It appears on an imported application's detail screen and, with the selected certificate/profile/options, on the signing screen. Admission starts a background scan; visible app screens rescan on opening, foregrounding, refresh, and every 60 seconds. The signing screen rescans when an identity, profile, or actual signing option changes. Signing forces a fresh package inspection and re-reads any saved profile before invoking the ten-stage signing engine and its pipeline. A diagnostic scan never signs, rewrites an IPA, accesses a private key, or installs anything.

## What is measured

The compatibility summary always shows the state of eleven check areas: package structure and availability; required metadata; main executable layout; bundle identifier; team identifier; selected certificate, capability metadata and expiry; authenticated profile, expiry, type, platform and device restrictions; requested entitlements; nested code and signing order; existing signatures; and the XML-only/DER option. These checks reuse the application's bounded archive reader, existing provisioning CMS/policy validation, and the signer's narrow Mach-O admission rule. An unreadable or unsupported input is not reported as a pass. The device rule can remain indeterminate when no target device is provided; no device ID is invented.

The **0–100 score** is the percentage of the eleven areas checked successfully: passed = 2 points, attention = 1, blocked/not checked/unsupported = 0. The denominator is always 22. Readiness is blocked when *any* area is blocked or unsupported, needs attention when another area is not passed, and ready only when all eleven have passed. Even a high score cannot override a blocked check. XML-only entitlements are an explicit warning, so current runs usually need attention even if other local checks pass. The score is **not** a prediction of certificate trust, Apple's static-code verdict, iOS acceptance, provisioning enforcement, installation, or runtime success. The issue inspector separates ZynSign's local evidence and proposed action from these platform-dependent outcomes.

DER entitlements are **not implemented by the application signer**. Requesting them is unsupported in diagnostics and refused by the pipeline *before* any archive or private-key work. Leaving the option off means XML-only output; it does not guarantee that an iOS target accepts it. Unimplemented bundle-ID rewriting or nested-code stripping are not offered as controls or recommendations.

Profile catalog summaries are display metadata, not a signing capability. Import now requires an authenticated and structurally valid CMS profile with a declared expiry. Selection reads the original stored bytes within the CMS input limit, reruns profile verification and policy for the current app and identity, and never replaces an unrepresentable or unauthenticated entitlement set with an empty one. If the stored file changes, disappears, or becomes unreadable, the signing action is blocked until it is inspected again. Profile/certificate library changes notify the signing screen; analysis keyed to the selection discards older asynchronous UI results. No private-key operation is part of diagnostics.

## Incremental results and history

A short-lived package cache is keyed to the library record and artifact reference and reused when only the selected identity, profile, or DER option changes. Artifact availability is rechecked on each scan; a missing/inconsistent artifact invalidates the package cache. The 60-second timeout and forced pre-sign scan bound stale package observations. Authenticated profile verification is cached briefly by SHA-256 of the profile bytes, while compatibility policy and expiry are evaluated again for the *current* app, identity, and time. Identity-registration changes clear that verification cache. The input archive is inspected on a background actor, not during SwiftUI body rendering.

Only the opaque app-record UUID, scan UUID, timestamp, score, readiness, counts and fixed issue **codes** are saved to the on-device diagnostics journal. No profile bytes, app bundle identifier, entitlement keys/values, certificate fingerprint, local file path or issue text is retained. Per-app history is capped at ten distinct observations; the total is capped at 1,000, with a 2 MiB read/write ceiling. Identical consecutive observations replace the latest timestamp without erasing earlier *different* observations. Changes compare the new code set against the preceding observation. A deleted app's history is removed; in-flight scans cannot reinsert it in that session. A corrupt or unrecognized journal is reported as unavailable, not silently treated as an empty record or overwritten. Schema v2 is the schema this feature writes; experimental v1 data has no defined migration and is deliberately rejected rather than guessed.

## Validation boundary

The baseline [external-validation record](external-validation.md) independently tested output with Apple's desktop `codesign` and documented an **application resource-seal rejection** plus iOS-format divergences (including the CodeDirectory version and missing DER entitlement slot). These issues are **not repaired by this read-only diagnostic feature**. Nothing in a successful health card or the application's own post-sign verifier supersedes that evidence. The existing host vector checks exercise synthetic signatures and report *no* iOS/device verdict. The Swift unit tests cover report/score semantics, caching and invalidation, history bounds/redaction, saved-profile handling and DER refusal; the Xcode simulator build and suite must be run on a macOS machine with Xcode.
